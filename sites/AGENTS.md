# Sites

- Site applications belong under `sites/<hostname>/` and participate in the root Bun workspace and build/check/test gates. Keep one root `bun.lock`.
- Poneglyph remains a reusable database; applications own their HTTP/MCP surfaces. Do not add application-specific rules to canonical storage or fork its implementation.
- The playground composes `@leostera/poneglyph-mcp` with its dataset, ingress/rate limiter and a graph-scoped RPC binding to `@leostera/poneglyph-worker`. The private service owns canonical actor assembly and deployment-configured graph permissions. The site owns no database entrypoint or HTTP reader adapter; the source imports are not a published npm embedding contract.
- The current playground hostname, `onepiece.poneglyph.dev`, is protected by Worker-scoped Cloudflare Access for members of the owner's personal Cloudflare account. MCP remains read-only. Hosted receipts currently cover the first 10% plus `remainder90` ordinals 0–827, with batch 827 committed under its separately pinned one-time retry after the original attempt was confirmed aborted; the next uncommitted ordinal is 828. The sole remaining import authorization covers only the hash-pinned `remainder90` plan and its two-day window through a separate writer binding. It does not authorize arbitrary writes, derived enrichment imports, caller-selected backend/graph, admin/probe routes, unrelated large workloads, resource deletion or publication. Require runtime-verified `ctx.access` for the exact app audience, reject browser Origins, and enforce separate fail-closed admission before parsing/storage. No email PIN or public bypass policies; OPTIONS authentication is not bypassed. Generic MCP composition remains anonymous internally; local Access simulation is not a hosted membership-policy test. See RFD0006 for exact plans, current progress and the requirement to stop/reconcile any future unknown batch using its original identity.
- Default checks are offline, including a finite native integration with tiny synthetic facts. Never trigger deployment, account lookups, a wiki/corpus load or benchmarks through build/check/test.
- Read `docs/rfds/RFD0006-public-read-only-mcp-playground.md` for the application boundary and rollout limits. A built server, advertised schema, empty response or passing fixture does not prove that the One Piece corpus was loaded.
